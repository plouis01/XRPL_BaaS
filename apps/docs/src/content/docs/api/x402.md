---
title: x402
description: HTTP 402 Payment Required protocol — XRPL-native settlement for API requests and agent payments.
---

RailForge implements an XRPL-native version of the HTTP 402 protocol so that
agents, scripts, and clients can pay for individual API requests with on-chain
settlement. Both **XRP** and **MPT** are first-class payment assets;
trust-line / issued-currency settlement is out of scope this sprint.

There are two product surfaces:

- **Mode A — RailForge-gated demo.** `/v1/x402-demo/echo` is gated by x402
  when `X402_DEMO_PAYEE` is set on the API server. Useful for dogfood,
  smoke tests, and SDK integration tests.
- **Mode B — Client-gated routes.** Clients run their own server and use the
  RailForge verifier (`POST /v1/x402/verify`) from their backend. Routes are
  registered via the management API or the dashboard.

## Protocol

### 1. Initial request → 402

The client sends a normal HTTP request. If the route is x402-gated and no
valid `X-PAYMENT` header is present, the server returns:

```http
HTTP/1.1 402 Payment Required
WWW-Authenticate: X402 realm="/v1/x402-demo/echo"
Content-Type: application/json

{
  "x402_version": 1,
  "intent_id": "x402_intent_4YB5GRG7J2EBSK41N31GKCVASR",
  "resource": "/v1/x402-demo/echo",
  "payee": "rEHMTjmCNgxiGzgUTpV4Y1MwYpFpYz7e7p",
  "asset": "XRP",
  "amount": "10000",
  "destination_tag": 3489274013,
  "expires_at": "2026-05-19T12:34:56Z",
  "facilitator_verify_url": "https://api.railforge.dev/v1/x402/verify"
}
```

Key fields:

| Field             | Type    | Notes                                                             |
| ----------------- | ------- | ----------------------------------------------------------------- |
| `intent_id`       | string  | `x402_intent_<26-base32>`. Stable for the intent's lifetime.      |
| `payee`           | string  | XRPL classic address. The settlement Payment's `Destination`.     |
| `asset`           | string  | `XRP` or `mpt:<48-hex>` (MPTokenIssuanceID). IOU not accepted.    |
| `amount`          | string  | Smallest-unit decimal integer (drops for XRP; raw units for MPT). |
| `destination_tag` | integer | uint32 derived from `intent_id` via CRC32. MUST appear on the tx. |
| `expires_at`      | string  | RFC 3339. 5 minutes from issuance.                                |

### 2. Settle on XRPL

The client builds, signs, and submits a `Payment` transaction to `payee` with
the quoted `amount` and `destination_tag`, then waits for validation
(`tesSUCCESS` on a validated ledger).

For XRP: `Amount` is the drops as a string.

For MPT: `Amount` is `{ mpt_issuance_id, value }`. The recipient (`payee`)
must have submitted `MPTokenAuthorize` for that issuance, and the issuance
must have `tfMPTCanTransfer` set for holder-to-holder transfers to be allowed.

### 3. Retry with `X-PAYMENT`

The client retries the original request with:

```http
X-PAYMENT: <base64(JSON.stringify({ intent_id, tx_hash }))>
```

On a valid header the server runs the verifier and (on success) serves the
gated response. On any failure the server re-quotes with a fresh intent and
a `reason` field.

### Verifier failure reasons

| `reason`           | Meaning                                                               |
| ------------------ | --------------------------------------------------------------------- |
| `not_found`        | Intent id unknown.                                                    |
| `already_consumed` | Intent already claimed by another tx.                                 |
| `expired`          | Past `expires_at`.                                                    |
| `tx_lookup_failed` | rippled `tx` command failed (network blip, unknown txid).             |
| `not_validated`    | Tx not on a validated ledger or non-`tesSUCCESS` result code.         |
| `not_payment`      | Tx is not a `Payment`.                                                |
| `payee_mismatch`   | `tx.Destination` ≠ intent `payee`.                                    |
| `tag_mismatch`     | `tx.DestinationTag` ≠ intent `destination_tag` (or fails CRC check).  |
| `asset_mismatch`   | `meta.delivered_amount` shape or MPT id doesn't match the intent.     |
| `amount_short`     | `BigInt(delivered) < BigInt(intent.amount)`.                          |
| `malformed_header` | `X-PAYMENT` header didn't decode (middleware-side; no verifier call). |

## Management API

### Register a gated route

```http
POST /v1/x402/routes
Idempotency-Key: <uuid>
```

```json
{
  "path_pattern": "/v1/your-resource",
  "payee_address": "rEHMTjmCNgxiGzgUTpV4Y1MwYpFpYz7e7p",
  "asset": "XRP",
  "amount": "10000"
}
```

Response `201 Created`:

```json
{
  "id": "<uuid>",
  "path_pattern": "/v1/your-resource",
  "payee_address": "rEHMTjmCNgxiGzgUTpV4Y1MwYpFpYz7e7p",
  "asset_kind": "xrp",
  "asset_key": null,
  "price_amount": "10000",
  "is_active": true,
  "created_at": "2026-05-19T12:34:56Z"
}
```

`409 Conflict` is returned if an active route with the same `path_pattern`
already exists on this tenant. Soft-deleted routes preserve the
`(client_id, path_pattern)` slot — recreate by deleting and re-posting.

### List

```http
GET /v1/x402/routes
```

```json
{ "routes": [ { ... }, ... ] }
```

### Delete (soft)

```http
DELETE /v1/x402/routes/{route_id}
```

`204 No Content` on success, `404 Not Found` if the route belongs to a
different client or doesn't exist.

### Remote verifier (Mode B)

Clients gating their own routes call this from their backend after
receiving an `X-PAYMENT` header from an end-user.

```http
POST /v1/x402/verify
Idempotency-Key: <uuid>
```

```json
{
  "intent_id": "x402_intent_4YB5GRG7J2EBSK41N31GKCVASR",
  "tx_hash": "DBB281B6C0F2DE35FB041BE167C3D9129ECE382B78F462D439F978B85FF6D246"
}
```

Response `200 OK` (the body always returns 200 — the `ok` flag carries the
verifier verdict; this avoids conflating "your request was malformed"
with "the payment they sent you was bad"):

```json
{
  "ok": true,
  "ledger_index": 17511292,
  "intent_id": "...",
  "consumed_at": "..."
}
```

```json
{ "ok": false, "reason": "amount_short" }
```

### Intent inspection (debug)

```http
GET /v1/x402/intents/{intent_id}
```

Returns the row with `payee_address`, `asset_kind`, `amount`,
`destination_tag`, `consumed_at`, `consuming_tx_hash`, and timestamps.

Mode A intents (created with a `client_id`) are visible only to their
owning client; Mode B intents (no `client_id`) are visible to any
authenticated reader.

## SDK quickstart

```ts
import { RailForge, type X402Signer } from "@railforge/sdk";
import { Client, Wallet } from "xrpl";

const sdk = new RailForge({ apiKey: "rf_test_..." });
const xrpl = new Client("wss://s.altnet.rippletest.net:51233");
await xrpl.connect();
const payer = Wallet.fromSeed(process.env.PAYER_SEED!);

// The SDK never touches the payer's key — the signer is yours.
const signer: X402Signer = {
  async signAndSubmit({ payee, asset, amount, destinationTag }) {
    const tx =
      asset === "XRP"
        ? {
            TransactionType: "Payment",
            Account: payer.classicAddress,
            Destination: payee,
            Amount: amount,
            DestinationTag: destinationTag,
          }
        : {
            TransactionType: "Payment",
            Account: payer.classicAddress,
            Destination: payee,
            Amount: { mpt_issuance_id: asset.slice(4), value: amount },
            DestinationTag: destinationTag,
          };
    const prepared = await xrpl.autofill(tx);
    const signed = payer.sign(prepared);
    await xrpl.submitAndWait(signed.tx_blob);
    return { tx_hash: signed.hash };
  },
};

const res = await sdk.x402.pay("https://example.com/gated-resource", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ hello: "world" }),
  signer,
});
console.log(res.status); // 200 once the payment validates
```

The `pay()` flow:

1. Issues the initial request.
2. If 402: parses the quote, calls your signer, awaits validation.
3. Retries the original request with the `X-PAYMENT` header set.
4. Returns the final response.

Non-402 responses are returned verbatim — the SDK never retries 4xx/5xx
that isn't 402. If the server re-quotes 402 (e.g. `reason=tag_mismatch`),
`pay()` will retry up to `maxRetries` times (default 1, hard cap 3).

## MPT specifics

- Intent `asset` for MPT is `mpt:<MPTokenIssuanceID hex>`. The 192-bit
  issuance id is 48 hex characters (not 64).
- The verifier reads `tx.meta.delivered_amount` and expects the post-
  `fixMPTDeliveredAmount` shape: `{ mpt_issuance_id, value }`. That
  amendment is active on mainnet + testnet (see [PLAN §7.4]).
- The recipient (payee) must hold an `MPToken` for the issuance — i.e.
  they must have submitted `MPTokenAuthorize` for that issuance. If the
  issuance also has `tfMPTRequireAuth` set, the issuer must whitelist
  the recipient separately.
- For holder-to-holder transfers (the typical x402 flow), the issuance
  must have `tfMPTCanTransfer` set. Without it, only issuer↔holder moves
  are valid and a payer-to-payee Payment fails with `tecNO_AUTH`.

## Limits

- Intent TTL: **5 minutes** from issuance.
- 402-issuance rate limit: **30 intents/min/IP** (configurable per mount).
- DestinationTag space: derived from CRC32 of `intent_id` modulo
  `0xFFF00000`. The upper `0xFFF00000–0xFFFFFFFF` band is reserved for
  future refund / retry flows.
- Intent IDs use 16 random bytes (~128 bits of entropy) encoded as a
  26-char Crockford-style base32 string (no `I`, `L`, `O`, `U`).

## Operational notes

- The intent reaper job deletes stale **unconsumed** intents past a 1-hour
  grace window (`expires_at < now() - 1h AND consumed_at IS NULL`).
  Consumed rows are preserved for audit.
- A single tx hash may not satisfy two distinct intents — enforced by a
  partial unique index on `consuming_tx_hash`.
- `consumeIntent` uses an atomic `UPDATE ... WHERE consumed_at IS NULL
RETURNING id` claim-once gate; two concurrent retries of the same tx
  hash never both succeed.
